# OntoBridge｜企业遗留系统 AI 连接与业务本体平台

产品设计方案 V1.0 · ERP / MES / WMS / OA / CRM · 面向传统企业 AI 转型

我认为这是一个非常值得独立产品化的企业 AI 基础设施方向，尤其适合制造业企业和 FDE 工程化交付场景。

传统企业推进 AI 转型时，一个普遍的问题是：

> 企业已经购买了 ERP、MES、WMS 等系统，积累了大量业务数据，但这些数据被封闭在各个软件内部。系统没有标准 API，业务对象无法统一关联，AI 即使能够读取数据，也无法理解企业真正的业务逻辑，更难安全地执行操作。

这里实际上存在三个不同的问题：

1. 连接问题：没有 API，怎么访问遗留系统的数据和业务功能？
2. 理解问题：ERP 里的销售订单、MES 里的生产工单、WMS 里的库存批次，如何关联成统一的企业业务模型？
3. 执行问题：如何把统一后的业务能力提供给 AI Agent，让智能体不仅能问数、分析，还能触发经过授权的业务动作？

我的产品判断是：

不要只做 ERP/MES 转 MCP 的工具。应该做一款“企业 AI 连接中台 + 业务本体引擎 + Agent 能力网关”。

MCP 应当是对外输出协议之一，而不是整个产品的底层架构。因为 MCP 本质上解决的是 AI 应用如何发现和调用工具、资源的问题，并不负责自动完成遗留数据库接入、业务数据关联、跨系统事务或者企业权限治理。

## OntoBridge

Enterprise AI Integration & Ontology Platform

让没有 API 的传统企业系统，也能成为 AI 可以理解和调用的业务能力。

核心客户

制造业、传统企业、系统集成商

最终产品不应该向客户销售“连接技术”，而应当销售三种可衡量的业务能力：

- 让原本孤立的系统形成统一数据视图。
- 让 AI 通过一致的语义理解销售、库存、生产、设备等业务。
- 让排产 Agent、经营分析 Agent、库存 Agent 等快速获得真实数据与受控操作能力。

这可以成为多个行业 AI 应用共享的底层平台，而不是每交付一个智能体就重新开发一次 ERP 接口。

这个架构有一个重要设计原则：

底层连接方式可以非常复杂，但上层业务接口必须足够简单、稳定。

例如，对 AI 而言，不应该关心订单来自 Oracle、SQL Server、Excel，还是某个老旧 Windows ERP。

它只需要访问一个稳定的业务能力：

`get_order_delivery_risk(order_id)`

内部由平台完成身份映射、数据获取、业务关系查询和交期风险计算。

## 三、第一层：无 API 系统连接引擎

这是产品最先需要突破的技术难点。

ERP/MES 没有 API，不等于完全无法连接。应该提供多种经过授权的连接方式，按稳定性、实时性和实施成本选择。

### 1. 六种连接模式

| 连接模式        | 适用条件       | 主要能力                    | 推荐优先级 |
| ----------- | ---------- | ----------------------- | ----- |
| 数据库只读连接     | 可获数据库访问授权  | JDBC/ODBC、视图、增量查询       | P0    |
| 文件与报表连接     | 系统可导出文件    | Excel、CSV、XML、SFTP、定时导入 | P0    |
| CDC 变更捕获    | 支持数据库日志访问  | 增量变更、事件同步               | P1    |
| UI/RPA 连接   | 只有桌面客户端或网页 | 自动操作、读取页面、导出报表          | P1    |
| 私有 SDK/接口连接 | 厂商提供接口或插件  | 定制读取、受控业务调用             | P1    |
| 工业协议连接      | 设备或网关开放协议  | OPC UA、MQTT、设备状态采集      | P2    |

这些技术路线都有成熟的参考实现。例如，Apache NiFi 已提供 JDBC 增量查询和 SFTP 文件接入能力；Debezium 支持多类数据库的日志级变更捕获；Power Automate Desktop 支持通过 Windows UI 元素操作没有 API 的应用程序。

### 2. 设计一个可部署的本地连接网关

OntoBridge Local Gateway

在客户内网部署一个轻量级连接服务，靠近 ERP/MES 数据源运行，承担连接、数据采集、缓存、增量同步及受控执行。

网关需要具备：

- 自动发现：扫描经授权的数据源、表结构、字段、视图及可访问报表。
- 低代码配置：通过表单建立连接，不要求实施人员逐一编写数据同步程序。
- 多模式同步：全量、增量、定时、文件触发，以及具备条件时的 CDC。
- 断点恢复：网络中断后恢复同步，避免数据遗漏与重复。
- 运行隔离：数据库账号最小权限、连接池限流、禁止高负载查询影响生产。
- 安全部署：支持内网独立运行，或通过企业授权的出站加密通道与控制平面通信。

实际部署建议将控制平面和数据平面分离。传统制造企业优先让业务数据停留在本地，云端只存放经过授权的配置和脱敏元数据。

### 3. 最棘手的情况：连数据库也无法访问

例如某工厂使用十多年前开发的 ERP，安装在 Windows 电脑上，只有账号密码和操作界面。

产品需要提供一套 UI Connector Studio：

UI 连接器设计流程

产品模拟

1. 选择需要连接的 ERP 窗口、网页或客户端
2. 录制授权用户操作，例如打开“订单管理”并导出报表
3. 识别页面元素、输入框、按钮与表格结构
4. 配置参数、等待条件、异常处理与结果校验
5. 封装成可调度、可监控的独立连接器
6. 将输出数据映射成标准业务对象

例如：

`ERP → 登录 → 订单管理 → 查询日期 → 导出 Excel → 解析 → 同步`

这是一种可行但有边界的方式：UI 改版、弹窗、验证码、桌面会话失效都可能导致连接失败。因此应优先使用数据库和官方导出能力，把 RPA 作为兼容方式，而不是整个产品的默认连接方式。

如果客户不允许数据库访问，也没有授权导出、接口或可运行的 UI 自动化方式，就无法承诺可靠的自动连接，只能先采用人工导入或推动厂商开放能力。

## 四、第三层：企业业务本体引擎是核心差异化

这里才是真正能形成长期产品价值的部分。

数据连接解决“能拿到什么”，本体引擎解决“这些数据究竟意味着什么，以及可以用它们做什么”。

可以借鉴 Palantir Foundry 的思路：将业务对象、对象关系、业务动作以及治理权限放入统一的可运营模型，而不仅仅构建数据仓库或知识图谱。

### 1. 从数据库表映射到业务对象

假设一家服装 ODM 工厂有三个系统：

| 系统  | 原始表 / 字段举例                       | 统一业务对象                |
| --- | -------------------------------- | --------------------- |
| ERP | `sale_order`, `delivery_date`    | SalesOrder 销售订单       |
| ERP | `item_master`, `style_no`        | ProductStyle 产品款式     |
| MES | `prod_task`, `task_status`       | WorkOrder 生产工单        |
| MES | `operation_log`, `finished_qty`  | OperationEvent 工序事件   |
| WMS | `stock_balance`, `available_qty` | InventoryBalance 可用库存 |
| WMS | `material_batch`, `batch_no`     | MaterialLot 物料批次      |

字段匹配只是第一步，更重要的是识别主键和业务身份、不同系统之间的粒度差异，以及真实的关联条件。

### 2. 建立业务对象关系图

服装制造本体示例 · 订单到交付

示意图中的连接关系需由真实单据引用或经过校验的业务映射建立，不能只根据字段名称推断。

本体必须支持三类关键能力：

对象 Object：订单、客户、SKU、工单、设备、班组、批次、供应商。

关系 Relation：订单对应哪些工单、工单使用哪些物料、工序由哪个班组完成、设备当前承担哪些任务。

动作 Action：获取订单状态、计算交期风险、创建排产草案、发起补料申请、提交生产异常。

### 3. 最重要的技术：跨系统身份关联

例如：

- ERP 订单号：`SO-2026-0088`
- MES 工单号：`MO-00231`
- WMS 发料批次：`LOT-8892`

平台需要通过真实的订单拆单记录、工单引用、工单物料需求和发料记录建立关联，而不是认为三个编号天然对应。

需要有一个 Entity Resolution（业务实体解析）模块。

其核心能力：

1. 给每个业务对象分配企业内部统一的 Canonical ID。
2. 保留来源系统、来源主键、映射时间和历史版本。
3. 支持一对多、多对多关系，例如一个订单拆成多个工单。
4. 使用确定性业务规则优先匹配，AI 用于提出候选关联和解释。
5. 对不确定或冲突的关联进入人工复核队列。
6. 保留完整数据血缘，能够回溯到原始 ERP/MES 记录。

尤其要防止 AI 把“款号相同”“客户名称相似”的记录直接判定为同一个订单。

### 4. 本体中还要包含业务规则

例如订单交付风险，不只是数据查询：

```
entity: SalesOrder
metric: delivery_risk
inputs:
  - planned_delivery_date
  - finished_quantity
  - remaining_operations
  - material_availability
  - capacity_calendar
calculation: delivery_risk_v1
source_policy:
  order: ERP
  progress: MES
  material: WMS
requirements:
  - source_freshness_check
  - business_rule_version
  - provenance
```

这里的 `delivery_risk_v1` 必须对应可测试的实际计算逻辑，不能只是给模型的一段自然语言提示。

对于生产分析，建议明确区分：

- 事实层：实际库存、实际产量、订单交期。
- 规则层：产能约束、工艺前后依赖、物料齐套规则。
- 推断层：延期概率、缺料风险、优化建议。

并对查询结果附加数据更新时间、业务口径、计算版本和来源信息，避免 Agent 把过期、缺失或推测数据当作确定事实。

### 1. 业务能力自动生成器

假设客户已经建立订单、工单、库存三个本体对象。

平台就可以辅助生成下面这些能力：

| MCP Tool                  | 业务含义     | 依赖对象      |
| ------------------------- | -------- | --------- |
| `get_order_360`           | 获取订单全景信息 | 订单、工单、库存  |
| `check_delivery_risk`     | 分析订单延期风险 | 订单、工序、产能  |
| `get_material_shortage`   | 查询物料缺口   | BOM、库存、需求 |
| `get_production_progress` | 查询生产进度   | 工单、工序事件   |
| `simulate_schedule`       | 运行排产仿真   | 产能、工艺、订单  |
| `propose_schedule_change` | 提交排产调整草案 | 排产计划、审批流  |

每一个 Tool 都应包含完整的参数 Schema、结果类型、调用权限、超时、错误处理、业务语义和测试用例。

MCP 规范本身支持向 AI 应用暴露工具、资源和提示模板，也明确强调模型调用工具时的人类控制与确认机制。

### 2. 一次封装，多 Agent 使用

当平台发布 `get_order_360` 后：

- 经营分析 Agent 可以使用它查询交付情况。
- 智能排产 Agent 可以使用它获取订单约束。
- 销售 Agent 可以使用它查询客户订单进度。
- 生产管理 Agent 可以使用它分析瓶颈工单。

这就是平台的复用价值：一条数据连接、一个业务本体、多种 AI 应用共享。

### 3. 典型 AI 调用链

用户提问：

> “下周要交付的订单中，哪些可能延期？原因是什么？能不能帮我调整排产？”

1. Agent 调用 `list_due_orders` 获取下周交付的订单。
2. 调用 `get_order_360`，根据本体关联 ERP 订单与 MES 工单。
3. 调用 `check_delivery_risk`，检查剩余工序、产能和物料齐套状态。
4. 通过排产求解器生成两个备选方案，比较延期订单数、换线成本和资源冲突。
5. 调用 `propose_schedule_change`，生成待审批排产草案。
6. PMC 人员确认后，通过经过授权的执行连接器提交到 MES，并回读确认执行状态。

由此实现从企业问数到企业行动的闭环。

## 六、Action Broker：解决无 API 系统的安全回写

这里建议独立设计一个 业务动作代理（Action Broker）。

必须区分三件事：

- AI 提出了业务建议。
- 平台接受并审批了动作请求。
- 原始 ERP/MES 确实执行成功。

这三个状态不能混为一谈。

标准业务动作生命周期

创建草案

规则预检

人工审批

执行提交

结果回读

完成对账

任何一步失败，都要保留执行记录和可恢复状态，而不能直接向 Agent 报告成功。

对于没有 API 的系统，可以按权限情况选择官方数据导入、厂商 SDK、授权 RPA 或人工执行。不能默认通过直接修改 ERP/MES 数据库来实现写回，因为业务校验、凭证、库存占用及系统事务可能不由数据库单表控制。

第一版建议只支持低风险的草案动作。涉及生产工单释放、库存扣减、财务凭证、设备控制的操作，必须满足业务校验、授权审批、幂等执行和执行后对账条件。不要让 LLM 直接控制 PLC 等现场设备。

## 八、技术选型：尽量复用成熟开源组件

我不建议从头开发数据库同步引擎、RPA 引擎和工作流调度器。

| 模块            | 建议技术                      | 自研重点       |
| ------------- | ------------------------- | ---------- |
| Local Gateway | Go / Java、Docker          | 安全连接、节点管理  |
| 数据连接          | Apache NiFi、JDBC/ODBC     | 连接器模板与发现   |
| 增量同步          | Debezium，或定时增量查询          | 数据一致性、断点恢复 |
| UI 自动化        | Playwright、Windows RPA    | 操作录制、重试、验证 |
| 统一数据存储        | PostgreSQL                | 标准对象与身份映射  |
| 本体关系层         | PostgreSQL 关系模型，必要时 Neo4j | 语义模型与关系查询  |
| 业务规则          | Python + 规则引擎             | 规则版本、指标定义  |
| 工作流           | Temporal 或轻量任务引擎          | 审批、回执、补偿   |
| 服务接口          | FastAPI / Spring Boot     | 企业业务 API   |
| MCP           | 官方 MCP SDK                | 语义工具发布和治理  |
| 前端            | React + React Flow        | 可视化连接和本体设计 |

技术上有几个取舍：

第一，不必一开始就上复杂知识图谱。 PostgreSQL 足以支撑第一版的对象、关系和身份映射。需要复杂多跳关系探索或图分析时，再引入图数据库。

第二，MCP 不是系统唯一协议。 同一套业务能力应可以输出 REST、MCP 和事件，让不同 Agent 框架都能使用。

第三，把数据服务和操作服务隔离。 查询接口可以高并发调用，写入动作必须经过业务策略、审批和受控执行通道。

第四，部署应优先支持私有化。 制造企业的生产数据和 OT 网络往往受到严格管控，内网网关、双向身份认证、密钥管理、审计，以及源系统行列权限继承要在平台层设计。

## 九、首个行业版本：聚焦制造业 ERP + MES

产品最容易陷入的陷阱是：一上来就想支持所有行业、所有系统、所有 Agent。

我的建议是以服装制造或离散制造作为第一个垂直行业，优先完成最有复用价值的业务本体。

### 首批标准本体

| 本体对象                | 核心业务作用    |
| ------------------- | --------- |
| Customer 客户         | 客户及订单归属   |
| SalesOrder 销售订单     | 交付需求及销售计划 |
| ProductStyle / SKU  | 款式、规格和品类  |
| BOM 物料清单            | 产品与物料需求   |
| WorkOrder 生产工单      | 生产任务执行    |
| Operation 工序        | 工艺路径与进度   |
| Resource 生产资源       | 设备、产线及班组  |
| MaterialLot 物料批次    | 批次追溯      |
| InventoryBalance 库存 | 库存和可用量    |
| QualityRecord 质量记录  | 检验与异常追溯   |

第一版并不需要做通用“全企业本体”。只要解决订单、生产、物料和资源之间的关联，就可以支撑智能问数、交期分析、缺料预警及辅助排产。

### 第一批验证业务场景

场景 A：企业经营智能问数

打通 ERP 销售订单与 MES 进度，让老板可以查询在手订单、未交付金额和生产风险。

场景 B：PMC 智能辅助排产

将工单、工艺、物料和设备产能提供给 OR-Tools / PyJobShop 等求解器，生成辅助排产方案。

场景 C：缺料与交期预警

通过订单 BOM、库存、物料在途及生产进度，识别生产缺料与延期风险。

这三个场景可以共享底层连接器和本体，不需要三套系统各自对接 ERP/MES。

## 十、商业化产品怎么设计？

我更倾向于设计成 平台软件 + 行业模板 + FDE 实施服务 的组合。

| 产品版本              | 客户           | 交付内容                 |
| ----------------- | ------------ | -------------------- |
| Starter 基础版       | 小型工厂、AI 开发团队 | 数据连接、标准 API/MCP、基础映射 |
| Professional 专业版  | 中型制造企业       | 多源接入、本体设计、业务工具、安全策略  |
| Enterprise 企业版    | 多工厂、集团       | 私有化、组织权限、跨工厂本体、统一运维  |
| FDE Partner 合作伙伴版 | FDE 服务商、集成商  | 行业模板、白标、连接器 SDK、项目管理 |

这里真正重要的商业资产，是可以不断复用的三个模板库：

1. Connector Registry：常见 ERP/MES 产品的连接器及版本兼容模板。
2. Industry Ontology Registry：服装、机械加工、电子装配等行业的标准业务本体。
3. Agent Capability Registry：标准化的订单查询、库存诊断、生产分析及业务动作能力。

商业模式可以按基础平台授权、系统连接数、行业本体包、私有化部署及运维服务计费；早期用 FDE 项目获取真实的连接器和本体模板，再逐步产品化。

需要避免把收费完全绑定 MCP Tool 数量，因为同一业务能力可以有不同的工具拆分方式，这个指标不稳定，也不直接反映客户价值。

## 十一、第一版 MVP：如何真正落地

建议做一个可以进客户工厂交付的最小可用产品，而不只是一个漂亮的连接器 Demo。

## MVP 的建议边界

目标：证明一个没有标准 API 的传统 ERP/MES 环境，能够支持真实的 AI 问数与业务关联。

| 接入范围 | 1 个 ERP + 1 个 MES，至少两种接入模式   |
| ---- | ---------------------------- |
| 本体范围 | 订单、工单、产品、工序、物料、库存等核心对象       |
| 能力输出 | 5–8 个经过验证的业务 API / MCP Tools |
| 业务场景 | 订单全景查询 + 交期风险诊断              |
| 执行范围 | 只读查询和业务动作草案，不直接写回生产系统        |
| 部署范围 | 本地网关 + 管理控制台 + MCP Server    |

### 建议实施顺序

1. 阶段 1：连接与数据诊断

   验证 ERP/MES 实际接入权限，识别核心数据结构，完成只读同步。判断是否存在厂商授权、部署和数据库访问限制。
2. 阶段 2：语义映射和本体建立

   在真实数据中识别订单、工单与物料关系，通过业务人员确认关联规则、状态定义和指标口径。
3. 阶段 3：MCP/API 生成

   将经过验证的本体查询封装为标准业务能力，接入一个实际的 Agent 应用。
4. 阶段 4：业务验证

   用客户真实订单进行历史回测和在线验证，对比源系统结果，评估数据一致性、时效性和业务价值。

验收指标建议至少包含：

| 指标     | 建议验收要求              |
| ------ | ------------------- |
| 关键字段映射 | 由业务负责人逐项确认          |
| 跨系统关系  | 重要关联可追溯、可人工纠错       |
| 数据同步   | 达到客户约定的时效 SLA       |
| 查询准确性  | 关键场景与源系统结果核对        |
| 数据来源   | 每次关键查询能够追溯来源和更新时间   |
| 权限与安全  | 越权查询阻断、审计完整、无未经授权写回 |

第一版不必追求实时同步所有系统，也不要承诺自动识别任意 ERP 的全部业务语义。真正的目标是把一个经过验证的接入流程，沉淀为下一家客户可复用的产品能力。

## 十二、产品最关键的三个护城河

1\. 遗留系统连接器资产

覆盖各种老旧 ERP/MES 的连接方式、特殊字段、报表模板、版本差异与故障处理经验。越多真实项目，连接成本越低。

2\. 行业本体与业务规则资产

真正有价值的不是数据库表结构，而是行业中的订单拆分、工艺关系、产能、物料占用、业务指标和状态转换规则。

3\. 经过验证的业务动作能力

从“能查数据”到“能安全协同业务执行”，形成可复制的审批、执行、回读和治理机制。

## 我的产品结论

我建议把 OntoBridge 定位为：

面向传统企业的 AI-Ready 业务连接与本体基础设施。

它和普通 ETL、iPaaS、MCP Server 的核心区别是：

| 产品类型         | 主要解决的问题                          |
| ------------ | -------------------------------- |
| ETL / 数据同步   | 如何把数据搬过来                         |
| iPaaS / 系统集成 | 如何让系统互相交换数据                      |
| MCP Server   | 如何让 AI 调用已有的工具和资源                |
| OntoBridge   | 如何把遗留企业系统转换成 AI 可理解、可组合、可治理的业务能力 |

从 FDE 商业化角度，这个方向有一个明显优势：既可以独立销售，也可以成为智能排产、智能问数、AI 客服、库存优化等多个解决方案共同依赖的技术底座。

我认为下一步产品设计最应该深入的，并不是先做 MCP Server，而是三个真正决定交付成功率的模块：无 API 数据源连接器设计器、AI 辅助本体映射工作台、业务能力自动生成器。

把这三个模块形成一个可演示、可部署、可复用的闭环，才有机会从单次 FDE 项目成长为标准化企业 AI 产品。
